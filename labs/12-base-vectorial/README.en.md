# Lab 12: Vector database in depth

**The question:** exact search with numpy, a hand-written HNSW and Qdrant: how much recall is
lost in exchange for speed, and what happens when there are filters?

## 1. Concept

Finding the vectors most similar to a question means computing the distance against **all** of them
(exact search). With 15 thousand vectors that is a matrix multiplication and takes 2 ms. With
millions it no longer is: you need **approximate** indexes (ANN), which look at a fraction of the
vectors and sometimes miss one of the true nearest ones. That "sometimes" is measured as
**recall against exact search**.

**HNSW** (Hierarchical Navigable Small World) is the index used by almost every vector
database, Qdrant included:
- A graph where each vector is linked to its M nearest neighbors. Searching is walking:
  from an entry point, move to the neighbor closest to the question, and repeat.
- To avoid crossing the whole graph in tiny steps, there are **layers**: the upper ones have few nodes and
  long jumps, the bottom one has all of them and short jumps (like a skip list).
- `ef` is how many candidates are kept while walking: more `ef`, more recall and
  slower.

`hnsw.py` implements it in about 120 lines to see each piece.

**Filters.** "Buscá solo en documentos de CABA" (search only in City of Buenos Aires documents) or "solo lo que este usuario puede ver" (only what this user can see). There are two
ways: search and then filter (post-filter), or filter while walking the graph. The
first is trivial and has a trap that the lab measures.

## 2. Method

- **Vectors**: all the chunks generated by the 8 strategies of lab 03, without repeats:
  15,506 real `bge-m3` vectors (1024 dimensions). Many are near-duplicates (the same
  text cut in similar ways), which is what happens in a real index with versions.
- **Queries**: the 72 questions in `evals/questions.jsonl`.
- **Ground truth**: the 10 nearest according to exact numpy. Recall@10 = what fraction of those 10
  each index returns.
- **Indexes**: exact numpy, in-house HNSW (M=16, ef_construction=100) with two rules for
  choosing neighbors, Qdrant in local mode (`QdrantClient(path=...)`) and the Qdrant server
  1.19.2 (official macOS binary, without Docker) with the same M and ef_construction.
- **Filters**: by jurisdiction (half of the vectors pass) and by document (1 % pass).

## 3. Results

Full numbers in [`results.md`](results.md). Recall@10 against exact search:

| Index | ef=10 | ef=50 | ef=200 | Build |
|---|---|---|---|---|
| In-house HNSW, nearest neighbors | 56 % | 68 % | 77 % | 22 s |
| In-house HNSW, **diversity heuristic** | 77 % | 90 % | **97 %** | 442 s |
| Qdrant server (run 1 / run 2) | 87 % / 80 % | 96 % / 88 % | 99 % / 95 % | 12–36 s |
| Qdrant local mode | exact: 99.7 % | | | 16 s |
| exact numpy | 100 %, 2 ms per query | | | 0 s |

Filters (recall against filtered exact search):

| Filter | Top 10 then filter | Top 100 then filter | Qdrant, filter during search |
|---|---|---|---|
| Jurisdiction (50 % pass) | 92 % | 97 % | **99.8 %** |
| One document (1 % pass) | 75 %, returns 7.6 of 10 | 95 % | **99.7 %** |

## 4. Conclusion

1. **How neighbors are chosen matters more than everything else.** With the obvious rule ("the M
   nearest"), a node's neighbors are all near-duplicates of each other and the graph ends up
   split into groups that do not connect: 77 % recall even while looking at 1,170 vectors. With the
   paper's heuristic (accept a neighbor only if it is closer to the node than to the neighbors
   already chosen) the links point in different directions: 90 % with ef=50. It is the reason
   this index works in practice.
2. **Qdrant in local mode has no HNSW.** `QdrantClient(path=...)` is a Python
   implementation that compares against all vectors (its code says so and it warns about it when creating
   payload indexes). It is exact and, at this scale, it is enough; but the indexes and the filters
   during search, which were the reason for choosing Qdrant in the SDD, exist only in the
   server. **Problem for the design:** the app (lab 16) starts in local mode for simplicity;
   moving to the server means changing the URL, but it has to be decided before there is volume.
3. **Post-filtering loses results exactly when the filter is selective.** Searching the top 10
   and filtering by document, on average 7.6 results come back and a quarter of the
   correct ones are lost. For permissions this is serious: a user with access to few documents would get
   worse answers. Filtering during search (Qdrant with a payload index) loses
   nothing. It confirms the SDD's decision: **the permissions filter goes in the database**.
4. **The recall of an approximate index is not a fixed number.** The same server, same
   data and parameters, gave 95 % and 99 % in two builds (it builds in parallel and the
   levels are random). It has to be measured with your own data rather than trusting a value.
5. **At this scale, numpy wins.** 15 thousand vectors are searched exactly in 2 ms. An ANN index
   starts to pay off with hundreds of thousands of vectors.

### Limits
- The latency of the second run is inflated: it shared the machine with lab 04.
- 72 queries; the recall figures have a margin of a couple of points.
